# ADR 002: 자체 백엔드 — NestJS + 공유 Postgres

**상태:** Accepted

## 결정

백엔드는 NestJS API 서버(`apps/api`)와 단일 공유 PostgreSQL로 구성한다. 인증은 자체 JWT + bcrypt, 실시간은 socket.io 게이트웨이, 보안은 API 가드(1차)와 PostgreSQL RLS(2차) 이중 방어로 운영한다.

## 배경

숲친구 월드는 유저가 근접할수록 밀도가 올라가는 B2C 서비스다. 이 구조에서 가장 먼저 한계에 닿는 것은 **위치 브로드캐스트 비용**이다.

동접 100명이 한 지역에 모이면, 각자의 위치를 모두에게 개별 중계할 경우 메시지 수가 인원 제곱으로 폭증한다. 이 비용을 인원에 **선형**으로 묶으려면, 서버가 좌표를 **섹터 단위로 묶어** 한 묶음으로 방송해야 한다.

섹터 묶음 방송은 단순 중계기로는 성립하지 않는다. 여러 유저의 좌표를 중간에서 합칠 **집계 주체**가 필요하기 때문이다. 이 집계 주체가 곧 자체 서버이며, 자체 백엔드를 두는 핵심 기술적 이유다.

전송량 자체도 함께 줄인다. 위치는 **5Hz**로 보내고, 정지 중에는 전송을 생략한다.

## 근거

| 항목 | 단순 중계기 | 자체 백엔드 |
|---|---|---|
| 위치 메시지 (100명 동접) | 개별 중계, 인원 제곱으로 증가 | 섹터당 5건/초, 인원에 선형 |
| 섹터 판정·속도 검증 | 클라이언트 신뢰 | 서버에서 판정 |
| 인증 | 외부 관리형에 종속 | 자체 JWT + bcrypt |
| 동시 접속 한도 | 플랫폼 상한에 묶임 | 서버 증설로 해결 |
| 데이터 정합성 | 서비스 경계로 분산 | 단일 공유 Postgres 트랜잭션 |
| 보안 | 단일 방벽 | API 가드 1차 + RLS 2차 |

## 적용

- **인증**: 자체 JWT + bcrypt. 액세스 15분 / 리프레시 30일, 시크릿 분리(`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`). `users.token_version`로 일괄 폐기. 소셜 로그인(카카오·구글) OAuth 2.0 Authorization Code 흐름을 AuthService에서 처리(코드 교환은 전부 서버에서).
- **토큰 보관**: 리프레시는 httpOnly 쿠키(Next 라우트가 관리), 액세스는 브라우저 메모리에 둔다. 액세스를 쿠키에 두면 WebSocket 접속에 못 쓰고, localStorage에 두면 XSS에 노출되므로 메모리에 둔다.
- **실시간**: socket.io 게이트웨이. 섹터 단위 묶음 브로드캐스트를 서버가 담당하고, 섹터 판정과 속도 검증도 서버에서 수행한다. 브로드캐스트되는 좌표는 실지형 위경도가 아니라 **씬 로컬 좌표**다(섹터 판정·속도 검증 모두 씬 좌표 기준).
- **DB**: 서비스가 늘어도 Postgres 하나를 공유한다. 서비스별 DB 분리는 결제-발급 트랜잭션과 `appearance_hash` 유니크 보장을 분산 문제로 만든다.
- **RLS**: 요청마다 트랜잭션 안에서 `SET LOCAL`로 `app.user_id`·`app.user_role`을 넣고 정책이 이를 읽는다. 핵심은 광고주 간 테넌시 격리다.

## 주의

- `SET LOCAL`은 반드시 트랜잭션 범위여야 한다. 전역 `SET`으로 걸면 풀에 반납된 커넥션에 값이 남아 다음 요청이 남의 컨텍스트를 물려받는다.
- API는 테이블 소유자가 아닌 전용 롤 `app_api`로 접속해야 RLS가 적용된다.
- `users.role`은 컬럼 단위 권한으로 수정을 차단해 권한 상승을 막는다. 역할 변경은 운영 경로로만 한다.
