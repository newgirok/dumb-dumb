# ADR 008: 자체 백엔드 전환 — Supabase 이탈

**상태:** Accepted
**대체:** ADR 002 (Supabase 통합 백엔드 허브)

## 결정

Supabase Auth·Realtime·클라이언트 SDK 의존을 걷어내고, NestJS API 서버
(`apps/api`)와 자체 Postgres로 전환한다. DB는 서비스가 늘어도 **하나를
공유**한다.

## 배경

ADR 002는 1인 개발자의 운영 공수를 근거로 Supabase 통합을 택했고, 그 판단은
초기에는 옳았다. 전환 사유는 운영 편의가 아니라 **B2C 규모에서의 비용
구조**다.

위치 브로드캐스트를 10Hz로 보내던 설계에서 유저 1명이 하루 1시간 플레이하면
월 약 108만 메시지가 나간다. Supabase Pro 기본 제공량이 월 500만이므로
**유저 4~5명이면 한도에 닿는다.**

다만 이건 Supabase 요금제 탓이 아니라 설계 문제였다. 자체 서버로 옮겨도
메시지 수는 같다. 그래서 두 가지를 함께 했다.

1. 전송량 자체를 줄임 — 5Hz로 낮추고, 정지 중엔 전송 생략
2. 서버가 섹터 단위로 **묶어서** 방송 — 개별 중계가 아니라 한 묶음

2번은 중계기인 Supabase Realtime으로는 불가능하다. 중간에서 합칠 주체가
필요하기 때문이고, 이것이 자체 서버가 필요한 유일한 기술적 이유였다.

## 근거

| 항목 | Supabase | 자체 |
|---|---|---|
| 위치 메시지 (100명 동접) | 개별 중계, 인원 제곱으로 증가 | 섹터당 5건/초, 인원에 선형 |
| 동시 접속 한도 | Pro 500 | 서버 증설로 해결 |
| Auth | 관리형 | 직접 구현 (JWT + bcrypt) |
| RLS | 유일한 방벽 | API 가드가 1차, RLS는 2차 |

## 적용

- **Auth**: `apps/api` 의 AuthService. access 15분 / refresh 30일,
  `users.token_version` 으로 폐기
- **토큰 보관**: 리프레시는 httpOnly 쿠키(Next 라우트가 관리), 액세스는
  브라우저 메모리. 액세스를 쿠키에 두면 WebSocket 접속에 못 쓰고,
  localStorage에 두면 XSS에 노출된다
- **Realtime**: socket.io 게이트웨이. 섹터 판정과 속도 검증도 서버로 이동
  (클라이언트 검증은 고쳐 쓰면 그만이다)
- **RLS**: `SET LOCAL` 세션 변수 기반. 핵심은 광고주 간 격리
- **DB**: 서비스가 늘어도 Postgres 하나를 공유한다. 서비스별 DB 분리는
  결제-발급 트랜잭션과 `appearance_hash` 유니크 보장을 분산 문제로 만든다

## 주의

- `SET LOCAL` 은 트랜잭션 범위여야 한다. 전역으로 걸면 풀에 반납된 커넥션에
  값이 남아 다음 요청이 남의 컨텍스트를 물려받는다
- API는 테이블 소유자가 아닌 `app_api` 롤로 접속해야 RLS가 적용된다
- 소셜 로그인(카카오·구글)은 이번 전환에서 빠졌다. 필요하면 OAuth 를
  AuthService에 추가해야 한다
