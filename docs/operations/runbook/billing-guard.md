## Mapbox 과금 폭탄

Mapbox 요청은 루트 3D 씬의 5시 미니맵(줌 16 고정, 조작 불가)과 대시보드 월드 지도(Standard 3D 건물, 줌 14~20 조작 가능)에서 나온다. 둘 다 같은 `NEXT_PUBLIC_MAPBOX_TOKEN`을 쓴다.

### 원인 진단 체크리스트

1. **토큰 도용 의심**: Mapbox 대시보드 → "Analytics" → 비정상적인 요청 패턴(IP, 도메인) 확인
2. **대시보드 월드 줌아웃**: 유저가 최소 줌(14)까지 줌아웃해 넓은 지역 타일을 대량 요청 (`lib/map/camera.ts`의 `setMinZoom`)
3. **이동 폭주**: 대시보드 월드 캐릭터가 GPS 튐·키보드 이동으로 빠르게 움직이며 새 지역 타일을 연속 요청
4. **지도 인스턴스 누적**: 라우트 전환 시 이전 지도가 `map.remove()` 없이 잔존 (미니맵·`WorldCanvas` 모두 언마운트 시 `map.remove()`를 호출하는지 확인)
5. **Map load 급증**: 루트 방문(미니맵)과 `/dashboard` 진입이 각각 Map load 1회라, 방문 수 급증이 곧 과금 증가다

### 즉시 조치

```bash
# 1. Mapbox 대시보드에서 Billing Hard Cap 즉시 설정
# Settings → Billing → Budget alerts → Hard Cap 활성화

# 2. 의심 토큰 즉시 Revoke
# Tokens → 해당 토큰 → Revoke

# 3. 새 토큰 발급 + 도메인 락 적용
# Tokens → Create token → Allowed URLs: https://서비스도메인.com
```

## socket.io 실시간 연결 과부하 + API 서버 부하

대시보드 월드의 위치·채팅 브로드캐스트는 월드 게이트웨이(`apps/api/src/world/world.gateway.ts`)가
처리한다(루트 3D 씬은 서버에 연결하지 않는다). 서버는 위경도 섹터(500m 격자) 단위로 좌표를 묶어
200ms마다(5Hz) 한 묶음으로 방송하므로, 부하는 동시 접속 수와 활성 섹터 수에 좌우된다. 접속 상태는
인스턴스 메모리에 있다. 트래픽이 특정 섹터로 쏠리거나 유령 채널이 쌓이면 CPU·메모리가 급증한다.

### 원인 진단

서버 메트릭과 로그로 판단한다(외부 대시보드가 아니라 게이트웨이 상태 기준).

1. **동시 접속 급증**: 게이트웨이 위치 상태 수(`playerCount` — 최근 30초 안에 `move`를 보낸 접속 수)와 인스턴스 CPU/메모리 확인
2. **핫스팟 섹터**: 방송 중인 섹터별 인원 분포에서 한 섹터에 인원이 몰렸는지 확인
3. **유령 채널 잔존**: 방(room)에 남은 소켓이 있는지 확인한다. `STALE_MS`(30초) 정리는 위치 상태만 지우고
   룸 참여는 유지하므로, 방 인원은 소켓 연결 해제나 섹터 변경 때만 줄어든다

### 즉시 조치

1. **섹터 채널 해제 로직 점검**: 클라이언트가 섹터를 이탈하면 해당 섹터 방에서 빠져야 한다.
   서버는 `requiredSectors` 재계산 시 이전 섹터를 `leave`하고, 소켓이 끊기면 위치 상태를 지운다. `flush`의
   30초 정리는 위치 상태만 지우고 룸 참여는 그대로 둔다. 이 경로들이 정상 동작하는지 확인한다.
2. **Prune 시 리소스 해제**: 클라이언트는 50m 이동마다 반경 450m 바깥 피어 오브젝트를 dispose하고
   (`lib/three/prune.ts`), 음성은 위치를 전송한 틱마다 40m 밖 피어를 구독 해제한다(제자리에 있으면 갱신하지 않는다). 이 두 경로로 시야에서 벗어난
   상대의 렌더·오디오 리소스가 해제되는지 확인한다(불필요한 상태 보유 방지).
3. **API 서버 스케일**: 게이트웨이는 위치 상태(`players`)를 인스턴스 메모리에 두고, "2명 이상인 섹터만 방송"도
   인스턴스마다 따로 판단하는 단일 인스턴스 전제다. 같은 섹터의 두 유저가 서로 다른 인스턴스에 붙으면 서로
   보이지 않으므로, 수평 확장하려면 socket.io 어댑터(공유 백플레인)와 위치 상태 공유를 함께 구현해야 한다.
   그 전까지는 단일 인스턴스를 수직 확장한다.
4. **일시 완화**: 극단적 폭주 시 방송 주기(`TICK_MS`, 200ms)를 늘리거나(부하 대비 프레임 감소)
   신규 접속을 일시 제한한다.

## LiveKit Cloud 사용량 초과

### 원인 진단

1. LiveKit 콘솔 → "Usage" → 일별 분(分) 소모량 그래프 확인
2. 특정 시간대 급증 패턴 확인 (이벤트·핫스팟 구간 의심)

### 즉시 조치

- 거리순 Top-8 구독 Capping이 정상 동작하는지 확인한다(`lib/voice/livekit.ts`의 `MAX_SUBS = 8`,
  `LEAVE_M = 40` — 40m 안의 가까운 8명만 구독).
- 혼잡 구간에서는 구독 반경(`LEAVE_M`)과 구독 상한(`MAX_SUBS`)을 임시로 줄여 구독 총량을 완화한다.
  전체 볼륨 반경(`JOIN_M = 30`, `lib/voice/spatial-audio.ts`)은 들리는 크기만 정하고 구독량에는
  영향이 없다.
- 룸 토큰 TTL은 1시간이지만 접속 중인 세션 길이에는 상한이 없다. 세션 길이를 제한해야 하면
  `VoiceManager.connect` 뒤에 상한 타이머를 건다.

```typescript
// 세션 최대 길이 강제 적용 (60분 초과 시 disconnect)
const SESSION_MAX_MS = 60 * 60 * 1000;
setTimeout(() => {
  room.disconnect();
}, SESSION_MAX_MS);
```

## 좌표 위변조/텔레포트 방어 발동

### 증상

- 대시보드 월드에서 특정 유저의 위경도 좌표가 비정상적으로 빠르게 이동
- 조작된 `move` 패킷이 특정 유저로부터 반복 유입

### 방어 동작

속도 검증은 서버에서 수행한다. 월드 게이트웨이는 `move` 수신 시 직전 위경도 좌표와 비교해
도보로 불가능한 속도(30km/h 초과)면 그 좌표를 **무시**한다(`isPlausibleMove`). 따라서
텔레포트 좌표는 브로드캐스트되지도, 다른 유저에게 렌더되지도 않는다. 정상 클라이언트도 전송 전에
같은 기준(`lib/geo/validator.ts`)으로 거른다.

### 즉시 조치

1. 게이트웨이는 폐기한 `move`를 로그로 남기지 않는다. 조작이 의심되면 소켓 수·섹터 분포와
   클라이언트 측 이상 징후로 판단한다.
2. 악성 유저의 세션을 막으려면 `token_version`을 올린다. 리프레시 토큰이 폐기되어 새 액세스 토큰을
   받을 수 없고, 남은 액세스 토큰이 만료(최대 15분)되면 재접속이 막힌다. 게이트웨이는 접속 시에만
   토큰을 검증하므로 이미 열린 소켓은 끊기지 않는다. API 인스턴스를 재기동해도 클라이언트가 처음 받은 액세스
   토큰으로 자동 재접속하므로, 차단은 그 토큰이 만료(최대 15분)된 뒤에 확정된다. 즉시 강제 퇴장시키는 수단은 없다.

```sql
-- 해당 유저의 리프레시 토큰 전부 폐기 (남은 액세스 토큰이 만료되면 재로그인 필요)
UPDATE users SET token_version = token_version + 1, updated_at = now()
WHERE id = '<user_id>';
```
